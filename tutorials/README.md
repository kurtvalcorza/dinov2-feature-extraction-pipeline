## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/dinov2_feature_extraction_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 3-file SHA-256 manifest inline (88 MB total) and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the generating revision, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Model acquisition:** `stage_missing_files(WEIGHTS_DIR, allow_download=True)` fetches only the manifest entries that are absent, from the Hugging Face Hub at the immutable revision (never `main`); `verify_snapshot` re-hashes every entry; `from_pretrained(weights_dir=WEIGHTS_DIR)` loads the verified files into timm's built-in `vit_small_patch14_dinov2` architecture with `num_classes=0` and additionally checks that the feature width equals `EMBED_DIM` (timm executes no remote model code). The notebook's only external dependencies are the pinned PyPI distributions and the Hub at that revision.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/dinov2_feature_extraction_input_manifest.json` with the schema, ceilings, per-input identifiers and observations, verdict, and one recorded rejection finding; `evaluation_report` (EVAL21) writes `outputs/dinov2_feature_extraction_evaluation_report.json`, whose verdict is **always** `not-measurable` — see the next bullet.
- **§20.6 obligations:** the embedding shape (`EMBED_DIM` = 384) and pooling policy (`POOLING` = `"cls"`, the class token after the final LayerNorm, L2-normalised), the per-image unit, the absence of any missing-data concept (every pixel of the 518 x 518 centre crop is visible to the encoder), the statement that embeddings are representations rather than predictions, and the export of identifiers (image id, pixel digest, size) alongside every vector are all stated and implemented.
- **No intrinsic metric (EVAL9):** the repository ships no metric helper, so `evaluation_report` is always `not-measurable`; it names the score semantics (a cosine similarity is not an accuracy or a calibrated score) and the downstream labelled tasks a real evaluation needs — retrieval mAP, linear-probe or k-NN accuracy, human-judged duplicate pairs. The pairwise cosine similarities the notebook prints are a qualitative check only. Recorded `SHOULD` deviation: EVAL11 (no baseline — none is meaningful without a downstream task).
- The default sample set is synthetic and generated in code; its embeddings are plumbing/sanity evidence only.
- `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- The upstream weight license is Apache-2.0; the notebook's References section links `docs/WEIGHTS.md` for the resolved provenance record rather than restating the stale `config.json` field.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
